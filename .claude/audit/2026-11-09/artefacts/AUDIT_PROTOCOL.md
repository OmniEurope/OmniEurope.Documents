# Contrat de revue du nouvel audit

Lire AGENTS.md, la décision actuelle et AUDIT_ARCHITECTURE.md avant la revue profonde. Aucun changement de code, test, seuil, exception, branche ou version. Aucun build concurrent, aucun outil Python. Sorties humaines en français. Ne pas lire le contenu de PLAN-008. Chaque registre et index appartient à un seul agent. Lecture complète Full par fichier, sans recycler les anciennes conclusions. Les binaires nécessitent une preuve native de lecture ou validation, pas une signature seule. Les observations non reproduites restent des pistes.

## Relevance gate (applies to EVERY mode, every reviewer, every persisted finding)

Token budget is spent on **pertinent** findings only. Severity is not the filter: a `Faible` finding with a real, provable consequence is kept; a `Moyen` finding that is a taste remark is dropped. A finding is **pertinent** when it passes all four tests; otherwise it is silently discarded (not written, not persisted, not counted, not rendered):

1. **Evidence** - it names the exact `file:line` (or the transcript turn) and the reviewer actually read that location this run. "Probably", "might", "could be worth checking" are not findings.
2. **Consequence** - it states an observable effect for this project: a wrong result, a crash path, a security hole, a broken or untested behavior, a claim the artefacts contradict, a rule from `AGENTS.md`/the code-rules registry violated, a doc that now lies. Style preference, theoretical purity, speculative future needs, and "would be nicer" do not qualify.
3. **Actionability** - Claude can fix or verify it end-to-end from the finding alone (or it is an explicit `BLOCKER` / `DECISION REQUIRED`).
4. **Not already handled** - not fixed later in the same session or run, not a duplicate of another finding (keep the sharpest phrasing), not a restatement of the pre-existing state of code this scope did not touch.

Caps (hard, after ranking by impact × confidence): **session audit ≤ 8 findings** (fixed + follow-ups combined), **360 audit ≤ 5 findings per file and ≤ 25 per module register**, and the cross-module synthesis lists at most the top 30. Anything beyond the cap is dropped, never appended as "minor". `RAS` is the expected, honest output for a clean file or dimension; a reviewer is never judged by how much it reports. `INFO` / positive / "observation" entries are not written anywhere except the single advisory `Proportionnalité` line and `[INFO] [Sur-ingénierie]` notices.

Each reviewer prompt must quote this gate verbatim; the orchestrator re-applies it when merging and drops anything that fails it, even if a sub-agent kept it.


### Audit criteria (per code file)

1. **Quality and proportionality**: readability, duplication, long methods, naming, error/exception handling, null-safety, dead code, magic numbers, plus mandatory anti-over-engineering comparison. Verify that every added abstraction, layer, dependency, switch, extension point, custom framework, or indirection serves a current requirement, actual caller, project rule, or measurable constraint. An over-engineering notification must include the concrete cost and a simpler behavior-preserving alternative; do not penalize complexity required for security, reliability, architecture, testability, or an observed second use case. Record it only as `[INFO] [Sur-ingénierie]`: it is advisory, non-actionable, excluded from findings and severity totals, and cannot affect completion or verdicts.
2. **Metrics** (from `metrics/`, not re-estimated by hand): cyclomatic complexity (> 10 flag, > 20 critical), god files/classes → propose split, CRAP score from `crap_report.md` (> 30 = priority).
3. **Style & conventions**: C#/.NET conventions, `.editorconfig`, usings, async/await, **no em dash character (U+2014) anywhere** in the file (code, comments, strings, docs) - it is never used in this project; flag every occurrence and recommend a hyphen `-`, colon, or parentheses - **plus the _Generic kit's `coding-standards.md` rules** at the file level (code-behind `.razor` + `.razor.cs`, no inline CSS, no `partial` except where required, localization via `IStringLocalizer`, one class per file…). Project-level kit conformity is Pass 1b; here it's the per-file granular rules. **Apply the code-rules registry** (the project's `.claude/code-rules.md` overlay + the kit-canonical `docs/code-rules.md`, resolved as in Pass 1b; overlay wins on same-ID): for every registry rule whose scope matches this file, run its *Detection* recipe and log a finding keyed by rule ID (`STD-PARTIAL`, `STD-BTN`, `STD-DIALOG`…). `analyzer`/`audit` rules are checked here per-file; `test`-layer rules (e.g. `STD-NAV`) are verified once at Pass 1b, not per file.
4. **Architecture**: conformance to the target (Pass 1), placement, coupling, dependency direction, abstraction leaks, SOLID. Confirm dead code via Roslyn MCP before flagging.
5. **Security**: cross-reference `metrics/SECURITY_SCAN.md` first, then supplement with manual review for what tools miss: injections, hardcoded secrets, input validation, authz/authn, data exposure, unsafe deserialization, SQL/EF queries. Where no SAST ran, label "best-effort, non outillé".
6. **Performance**: needless allocations, N+1, blocking I/O, mishandled async, IDisposable / unreleased resources.
7. **Reliability**: coverage (from reports), edge cases, logging, observability.
8. **Authenticité (anti-fake)**: detect work faked to look complete rather than actually done - **stub/placeholder shipped as real** (`NotImplementedException`/`NotSupportedException` in concrete code, empty bodies, a hardcoded/constant return standing in for real computation, `return null`/`default`/`Task.CompletedTask` where a real result is expected, `// TODO: implement` left in a path treated as finished, canned/fake sample data in a production path); **checks gamed instead of satisfied** (`#pragma warning disable`, `[SuppressMessage]`, `<NoWarn>`/`$(NoWarn)`, analyzer/test suppression, disabled or skipped tests `[Fact(Skip=…)]`/`[Ignore]`, lowered coverage/quality thresholds); **tests that don't test** (always-true assertions, asserting only on a mock's own return, swallowed exceptions, commented-out assertions); **functionality silently disabled** (dead early `return`, short-circuited branch, feature flag off, removed route/DI registration) while documented as working. Flag each with its line and the real-vs-claimed gap; map to the `Authenticité` category in findings.
9. **UI / Radzen** (frontend files): where a Radzen component exists for the need (e.g. `RadzenTimeline`, `RadzenDataGrid`, `RadzenScheduler`, `RadzenChart`, `RadzenDialog`), it MUST be used instead of hand-rolled HTML/CSS/JS. Flag any custom implementation that duplicates an available Radzen component, and any raw `<table>`/`<select>`/custom widget that has a Radzen equivalent.

### Additional criteria - test files

Same criteria, PLUS: relevant (tests real useful behavior)? Actually tests something (no trivial/always-true assertion)? Covers edge cases + error paths? Deterministic? Relevant mocks, no over-mocking? Clear Arrange/Act/Assert; one behavior per test.
